# Grid and viewer: virtual grid, list panel, thumbnails, selection, sort, full screen, compare, marking, drag-and-drop, slideshow (main.js, part 2 + list-view.js + fullscreen.js + preview-zoom.js + drag-drop.js)

## Purpose
What the user looks at and acts on: the virtual thumbnail grid (square, framed, justified, masonry), the thumbnails pipeline that feeds it, selection, sort and date/name separators, the preview panel with zoom and **compare mode** (up to 4 photos, `src/preview-zoom.js`), drag-scroll and photo drag-and-drop (`src/drag-drop.js`), full screen, the slideshow, and the marking actions (rating, colour, pick, lossless rotation) with their undo. Loading the photo list and the task queue are in `main-window.md`; the filters that build the displayed list are in `filters-and-search.md`.

## How it works

### Two lists, one grid
`loadedPhotos` is what the backend returned; `photos` is the displayed list built by `applyPhotoFilters` (filters, then sort). Every grid and viewer function indexes `photos`. `selectedIndices` (a Set of indices into `photos`) and `lastSelectedIndex` (the **active photo**: target of keyboard navigation, Info panel and full screen) are shared state. Anything that rebuilds `photos` must re-find the selection by path (`applyPhotoFilters({keepState:true})`).

### Virtual grid (⚠ sensitive, pixel-exact)
1. `updateVirtualScroller` measures `gridContainer.clientWidth − 2·GRID_SIDE_MARGIN` (8 px, room for the 3 % hover zoom without a horizontal scrollbar), computes `photoLayouts` (`{index, x, y, width, height}`) and `separatorLayouts`, and sets the height of `scrollContent`. With separators (`computePhotoGroups`: by day/week/month/year when sorted by date, by folder when sorted by name, duplicate groups in duplicate mode, none for content search) each group is laid out on its own.
2. `layoutPhotoRange` does one group: **square/framed** (columns from `thumbnailSize` capped by `devicePixelRatio`), **justified** (rows filled until the row height fits under the ceiling `thumbnailSize / ratio`; the last row of a group is **not stretched**, left-aligned, height capped), **masonry** (shortest column first, ratio clamped 0.2–5, height capped by the cache resolution `thumbnailCacheSize`, `object-fit: cover`). A photo is never displayed larger than its cached thumbnail (the cap is on the longest side).
3. Display > Thumbnails Grid also stores `thumbnailCorners` (`no`, `light`, `medium`, `strong`, `max`). CSS applies percentage radii; `max` is 100%, which makes square thumbnails circular. Rounded corners require a gap, so choosing any rounded value changes `thumbnailSpacing` from `none` to `small` and disables `none` until rounding is turned off.
4. `renderVisibleItems` binary-searches `photoLayouts` for the visible window plus one screen of overscan (`THUMBNAIL_OVERSCAN_SCREENS`), creates missing DOM nodes (cached in `renderedThumbnailNodes`) and only writes style/class when a value changed (`div._transform`, `_width`…). Nodes are positioned with `translate3d`; selection is a class and an outline-like `.selection-ring` element, never a size change (AGENTS.md §7: no reflow). Scrolling also shows the temporary `#grid-scroll-position` pill: its first visible photo gives the taken/modified date or filename used by the active sort.
5. `photoAspectRatio` = ratio learnt from the loaded image, else EXIF width/height from the catalogue, else 1. When a thumbnail loads with a different ratio, `learnPhotoAspectRatio` → `scheduleJustifiedRelayout` (80 ms debounce, ignored for masonry except videos, whose size is not in the catalogue).
6. Layout rules in px are in AGENTS.md §5.A / §7: use `rem` only outside these calculations.

### Thumbnail pipeline of the grid
1. `loadThumbnail(image, path, photo)` → `lookupCachedThumbnail`: all paths requested in one render are collected and sent in batches of 128 to `get_cached_thumbnail_paths` (memoised per path in `thumbnailCacheLookups`).
2. Hit: `showCachedThumbnail` (asset URL + `versionSuffix`), ratio learnt on load.
3. Miss: `enqueueThumbnailGeneration`. The queue runs at most `MAX_THUMBNAIL_GENERATIONS` = clamp(cores − 1, 2, 6) jobs; `takeNextThumbnailGeneration` drops jobs whose image left the DOM, then picks the job **closest to the viewport**; jobs of a hidden grid wait; standalone requests (faces / people views, `enqueueStandaloneThumbnailGeneration`) go first, newest first. Job: `generate_thumbnail` (backend writes the cache file, returns path and size).
4. Backend failure: file really gone → `checkPhotoMissing` (see `main-window.md`); video → empty cell with its play icon; RAW without a usable preview → `markFormatPlaceholder` (format letters shown, never demosaiced); otherwise **webview fallback** `generateThumbnailInWebview` (≤ 2 at once; decodes the original, then `cacheThumbnail` → `save_thumbnail_cache`).
5. Modified files: `photoVersions` adds `?v=<time>` to URLs so a rewritten image is not served from the webview cache.

### Orientation, `view_fix`, RAW / HEIC / video in full screen
- The webview applies only the EXIF orientation of an original. When the winning orientation is XMP (sidecar), the backend sets `photo.view_fix` (1–8) and the frontend applies the rest (`orientationMatrix`, `swapsSides` from `src/orientation.js`; used in `layoutPreviewSlot` in `preview-zoom.js`, canvas fallback). Cached thumbnails and generated previews are already turned: their `view_fix` is 1. Rules of precedence: `orientation::resolve` (see `thumbnails-and-previews.md`).
- `getPhotoDisplayUrl`: normal formats use the original (`photoUrl`); RAW, HEIC/HEIF and videos (`needsGeneratedPreview`) call `get_raw_preview_path` once per photo (promise memoised in `rawPreviewPromises`; failure is not memoised; a video never falls back to the file itself).
- Extension lists (`RAW_EXTENSIONS`, `HEIF_EXTENSIONS`, `VIDEO_EXTENSIONS`) come from `format-filters.js`; `isRawPath` and `isVideoPath` (`src/file-kinds.js`) test a path against them. Videos are never played inside the app: `openFullscreen` sends them to `open_video_externally`.

### Full screen
`openFullscreen(index)` (`src/fullscreen.js`) → selects that photo only, `loadFullscreenPhoto` → `showFullscreenPhoto` (waits for `decode()` of an off-screen image, the element `preloadFullscreenImages` already started when there is one, then applies size/zoom in one step so no stretched frame appears; `fullscreenLoadToken` discards stale loads), `preloadFullscreenImages` (±2 neighbours + the next slideshow photo are loaded, `fullscreenImageCache` keyed **by index**, so it is cleared via `clearFullscreenImageCache()` on any re-sort; the 2 photos ahead in the direction of travel (`fullscreenDirection`, updated via `setFullscreenDirection`) and the one just left are also decoded in advance, see "Decoding" below). Grid navigation (`navigateToPhotoIndex`, arrows, wheel) keeps the active thumbnail visible with `scrollPhotoIntoView`; Up/Down (`navigateGridRow`) first pick the photo above/below from `photoLayouts` boxes (nearest facing edge, then closest centre; works in every layout). `updateUIOnSelection` then reloads. Zoom/pan share the preview's slot logic (`layoutPreviewSlot` in `preview-zoom.js`, `fullscreenSlot` in `fullscreen.js`). An image error calls `checkPhotoMissing`. Closing stops the slideshow.

- **Decoding.** A 42 MP JPEG takes about 200 ms to decode. Assigning it to the visible `<img>` right after `onload` made the compositor wait for that decode: a DevTools trace showed the main thread blocked 245–295 ms per change of photo (the JavaScript of the wheel handler was only about 12 ms). So the image is decoded by `decode()` on an off-screen element first. `queueFullscreenDecode` / `pumpFullscreenDecodes` decode in advance `FULLSCREEN_DECODE_AHEAD` (2) photos in the direction of travel and `FULLSCREEN_DECODE_BEHIND` (1) behind, **one at a time**, skipping a photo that is no longer wanted when its turn comes: a decoded 40 MP image weighs about 170 MB and the webview keeps decoded images in a limited cache, so the window must stay small. Whether the decoded pixels are reused when the visible `<img>` receives the same URL depends on the webview's cache: check with a trace after changing these constants.
- **Thumbnail as fast preload** (setting `fullscreenThumbnailPreload`, off by default, Settings > Storage > Thumbnail cache). If the sharp image is still not shown `FULLSCREEN_THUMBNAIL_DELAY_MS` (40 ms) after the request, `showFullscreenThumbnail` displays the cached thumbnail (`lookupCachedThumbnail`, the grid's lookup) at the size the photo will have: its own ratio and the longest side of the catalogue size (orientation does not matter) or of the window when the catalogue has none. `apply` then swaps in the sharp image. A photo without cached thumbnail shows nothing more than without the option. The picture is soft for the time of the decode.

### Selection and Info panel
`handleSelection(index, event)`: Shift = range from `lastSelectedIndex` (stops at the compare limit), Ctrl = toggle, plain = replace. `canAddToSelection` (`preview-zoom.js`) enforces `MAX_COMPARE` = 4 **only in compare mode**. `updateUIOnSelection` is the single fan-out after a selection change: keywords/description/location panels, `renderVisibleItems`, rating/colour bars, `renderPreview`, Info panel fields, map, histogram. The Info panel's Folder row shows the active photo's folder in All Photos, when subfolders are included, and in manual or smart album views; clicking it navigates to that folder in the tree. Hovering the "Date taken" row shows a tooltip with the **file's** creation and modification dates (`file-dates.js`): `updateUIOnSelection` calls `renderFileDates(photo)` (or `null` with no photo), which only remembers the active path and clears the previous tooltip; the dates are read from the disk by `get_file_dates` on `mouseenter` (one `stat`, nothing is read while browsing), and a stale answer is dropped (counter + path check). They are never taken from the catalogue: `photos.created` is exposed on `Photo` for the List panel only (filled at scan time, 0 if unscanned) and `photo.modified` is only the last value the scan stored. A date the file system does not provide (creation date on some Linux file systems) or a missing file (unplugged disk) is shown as "-".

### Preview and compare
Implemented in `src/preview-zoom.js` (section "PREVIEW: ZOOM, PAN AND COMPARE MODE", wired via `initPreviewZoom` in `main.js`). `renderPreview` fills `previewSlots` (one per selected photo in compare mode, shared centre unless "Desynchronise"; exposed via `getPreviewSlots` / `layoutPreviewSlots`, invalidated on photo move/rotation/sync via `invalidatePreview`), zoom steps ×1.4 up to 200 % (`zoomPreviewSteps`, `togglePreviewActualSize`, `getHoveredPreviewSlot`). In compare mode with several photos (`isCompareMultiple`), commands (rating, colour, delete, rotation) target only the **sub-selection** (`compareSubSelection`, circle-check marks in the preview): `commandTargetPhotos`. Context-menu commands always target the right-clicked photo. Leaving compare restores the preview's previous visibility.

### Instant zoom (hold Z)
Section "INSTANT ZOOM (HOLD Z)" of `src/preview-zoom.js`, built on the preview primitives (`zoomPreview`, `zoomPreviewSteps`, `previewSlotsToAffect`, `setPreviewCenter`, `clampPreviewCenter`, `renderPreviewTransforms`). Holding plain **Z** (character, so the AZERTY "Z" key; Ctrl+Z stays undo; Shift/Alt/Meta ignored) while the pointer hovers a preview cell (compare included) or the fullscreen photo sets zoom to 1:1 (`INSTANT_ZOOM_LEVEL` = 1); releasing it restores the zoom and centres saved at press time. The hovered slot is found with `document.elementFromPoint` on the last `pointermove` position (`instantZoomPointer`: a key event carries no coordinates). Affected slots = `previewSlotsToAffect(target)`: all loaded previews, or only the hovered one with "Desynchronise" (fullscreen: its own slot).
- Keyboard: `keydown`/`keyup` listeners in capture phase on `window`; once taken, Z is swallowed (`stopImmediatePropagation`) so e.g. the Faces-view letter keys do not fire. Ignored when a modal is open, on key repeat, and (preview only) when a text field/select/textarea has focus (`isTextEntryFocused`). Fullscreen skips that focus test.
- Pan: absolute mapping of the pointer over the image **fitted** in the target cell (`instantZoomCenterAt`), so the point under the cursor at press is the one centred and sweeping the fitted image reaches every edge. `pointermove` is coalesced with `requestAnimationFrame`; skipped while a mouse button is down (the usual drag pan keeps priority).
- Wheel: capture-phase `wheel` listener active only while Z is held; it replaces the fullscreen photo-navigation and the Ctrl+wheel zoom, uses `wheelZoomSteps` and `zoomPreviewSteps` with the same limits as + / -, then re-applies the pointer centre.
- End: `keyup` of Z, window `blur` and `visibilitychange`. If the displayed photo changed meanwhile (arrows, new selection, fullscreen closed: `isInstantZoomValid`), nothing is restored on the new photo.
- UI texts: shortcut row in `src/guide.js` + keys in `src/locales/en.json` / `fr.json`.

### Sort
`photoSortValue` (name with numeric collation, modification date, taken date; missing values go last whatever the order). The modification date is `photoModifiedTime(photo)` = the later of `photo.modified` (image file) and `photo.effective_modified` (image or sidecar, returned by every metadata write), the same rule as `db::EFFECTIVE_MODIFIED`; `photoSortDateParts` and `formatGridScrollPosition` use it too. After a write, `applyEffectiveModified(entries)` copies the new dates onto the photo objects of `loadedPhotos`, `folderTreePhotos` and `photos`, and when `sortKey === 'modified'` it clears `fullscreenImageCache` and returns true: the caller then runs `applyPhotoFilters({ keepState: true })` (selection kept by path, so Alt + digit "rate and advance" keeps going from the right photo). On a capped or paged view only the loaded page is re-sorted (the photo goes to the top of its page; a page load or sort change restores the exact global order). The list is sorted in the UI, but `get_photos_paginated` also receives `sortKey` / `sortOrder` because a capped or paged list (50 000 per page) must pick the right photos: `applySortChange` reloads from the backend (back to page 1) when `photoListCap` is set or the view has several pages (`photoPageCount > 1`), else re-applies filters and scrolls to the active photo. Persists `photoSortKey`, `photoSortOrder`, `photoDateSeparator`, `photoNameSeparator`.

### Page bar (views above `PHOTO_LOAD_LIMIT`)
A view with more than 50 000 matching photos (prefilter applied) is shown one page of 50 000 at a time; how the page is read is in `main-window.md` ("Loading the photos", step 4b). Section "PAGINATION DE LA GRILLE" of `main.js`, markup `#photo-pager` in `index.html` (styles `.photo-pager*` at the end of `styles.css`).
- The bar is a `position: sticky; top: 0` row of the grid, like the RAW / duplicates / content banners (so it shifts the grid down by its own height; the virtual scroller's overscan covers it). It is `hidden` while `photoPageCount <= 1`, i.e. for any normal collection, album or search mode.
- Content: previous button, a menu of pages (`Page N`), the text "of N", next button. A visually hidden `role="status"` element carries the full sentence ("Page 2 of 3") for screen readers. The tooltip of "of N" gives the photo range of the page out of the real total (`photoPageTotal`). `renderPhotoPager` redraws it from `currentPhotoPage`, `photoPageCount` and `photoPageTotal` (called by `adoptListResult` and on language change); the menu is rebuilt only when the page count changes.
- `goToPhotoPage(target)` (buttons, menu, **Alt + PageUp / Alt + PageDown**): clamps the target; ignored while `photoPageBusy`. If `hasSelectionEdits()` it asks through `resolvePendingSelection([])` (`metadata-writes.js`: the same Apply / Ignore / Cancel question as a selection change; Cancel stays on the page). Then it clears `selectedIndices`, calls `updateUIOnSelection()`, sets `currentPhotoPage`, clears `fullscreenImageCache` (index-keyed), `await loadPhotos()` and puts `gridContainer.scrollTop` at 0. While it runs the bar is greyed (`.busy`, `aria-busy`, controls disabled).
- The keyboard shortcut is its own `keydown` listener, inactive in full screen, behind an open window and in the Faces / People views. It is listed in `guide.js`.
- The sidebar counter (`updateFilteredPhotosCount`) reads "shown of total" with the whole view's total on a paged view, not the size of the page; the "list is cut" ⚠ only remains when paging is impossible (Ctrl+click folders).
- Filters that are not part of the SQL prefilter only narrow the loaded page.

### Marking, rotation, undo
1. `setSelectionRating / ColorFlag / PickFlag` pick targets, compute the final value (same value on all targets = clear it; pick buttons use `toggle:false`), then call `writeMarking(targets, fields, {apply, refilter,…})`.
2. `writeMarking` chains onto `markingChain` (writes run one after another, in key order), refuses photos of a running move, remembers the previous values, and calls `runLocked('update_photos_marking', …)` (direct under 20 photos, queued task from 20, see `metadata-read-write.md`). Only photos in `result.written` are updated in memory and in the grid (`apply`), `forgetCachedImagePaths` drops stale caches, `refilter()` re-runs the filters if one concerns the changed value. Failures are listed in the toast ("Details"), never reported as written.
3. `rotatePhotos` (Ctrl+R right, Shift+R left; Ctrl+R is always caught so it never reloads the window) follows the same shape with `rotate_photos`; the backend returns each photo's new `view_fix`; `isRotatablePath` excludes video and HEIC/HEIF.
4. Undo (`src/undo.js`): maintains two 20-entry LIFO stacks (`common` and `faces`, `MAX_UNDO`); each entry checks `canRun()` (which may be async, keeping the entry on the stack if it returns `false`) before popping, and an undo is not stacked again. Metadata-rewriting entries (`undoMarking`, `undoRotation`) record each file's `effectiveModified` after the write; on Undo, `canUndoFileTargets` calls `check_external_modifications` (zero cost otherwise) and asks confirmation via `confirmDialog` if any file or active sidecar was modified externally. `formatUndoToast` formats unified `Undone: …` messages with context-aware `photo`/`video`/`file` nouns (`itemKindForPaths`, single-file name when `count === 1`). Forward toasts offer `Undo` + `History` (`undoToastActions`); undo toasts offer `History` (`historyToastAction`) when entries remain. `#undo-modal` (`Ctrl+U`, capture-phase listener blocking browser View Source) displays only the active stack (`'faces'` in the Faces view outside full screen, `'common'` elsewhere) with an `Undo` button on the 1st row only and `Ctrl+Z` undoing that row while open. Producers on `common`: `undoMarking`, `undoRotation`, `undoSingleRename` (`renamePhotoOnDisk`), `batch-rename.js`, and fullscreen/preview face-overlay edits (`faces-panel.js`).

### Dragging
Implemented in `src/drag-drop.js` (wired via `initDragDrop` in `main.js`):
- **Grid drag-scroll** (section "GRID DRAG-SCROLL"): beyond `GRID_DRAG_THRESHOLD` (5 px) a press-and-drag scrolls the grid, with exponential inertia on release (`GRID_INERTIA_*` constants); `suppressGridClick` (capture-phase click handler) stops the release from also selecting.
- **Drag to the folder tree, manual albums and map** (sections "PHOTO DRAG-AND-DROP" and "FOLDER DROP ACTIONS"): Shift + drag moves the selected photos to a folder (`movePhotosToFolder`), Ctrl + drag copies them (`copyPhotosToFolder`), and dropping without a modifier opens `askCopyOrMove`; only the grabbed photo is dragged if it is not selected; Esc cancels. `folderItemAt` uses a descendant selector so sticky pinned folder rows (`li.folder-tree-sticky`) work as drop targets too. Dropping on a manual album adds or moves between manual albums (`albums-panel.js`: `addPhotosToAlbum`, `movePhotosToAlbum`), never moves disk files into an album; dropping on the map assigns a pending position (`map-mode.js`: `dragOverMap`, `dragLeaveMap`, `dropOnMap`). Mode follows the keys held at each instant (`dragModeFrom`).
- Dragging details: `src/drag-drop.js` (`initDragDrop`) handles grid drag-scroll and drag-to-folder/album/map; `slideshow.js` reads delay/loop/random settings.

### List panel (`src/list-view.js`)
Shares `#preview-panel` vertically with `#preview-stage` (`.main-content.list-mode`, mutually exclusive with People, Faces and Map modes). Zero work runs while closed. When open, `refreshListView` shares `photos`, `selectedIndices` and `lastSelectedIndex` bidirectionally with the grid (synchronizing row/grid scroll, `Shift`/`Ctrl` visual-range selection, double-click full screen, and right-click context menu via `.list-row` in `photo-actions.js`). Sorting supports up to 9 levels (`listSort`, `Ctrl+Click`, missing values always last) and optionally drives the thumbnail grid too (`listSyncGridSort`, on by default): when active, group separators are hidden and live metadata edits defer re-sorting until the next grid refresh; paged/capped views (> 50 000 photos) disable grid sync (local list sort still runs) and Duplicate / Content search orders stay prioritized. Columns (`listVisibleColumns`, `listColumnOrder` with `filename` pinned first, `listColumnWidths`, including the `File` submenu with `extension`, `file_size`, `date_created`, `date_modified` and the `Format` submenu with `resolution`, `megapixels`, `orientation`, `ratio`) gate optional features (`color_flag`, `pick_flag`, `analysed`, `faces_status`) and lazily load `get_analysed_photo_ids` (only when `isSemanticEnabled()`), `get_phash_states` (`phash` column: Yes / No (expired) / No), and `get_exact_hash_states` (`exact_hash` column under `Other data`: Complete / Pre-pass / No (expired) / No) when shown; hiding a column drops its sort.

## Invariants and sensitive areas
- ⚠ sensitive: virtual grid layout is pixel-exact (AGENTS.md §5.A/§7); a fractional width or a size change on hover/selection creates gaps or reflows.
- ⚠ sensitive: `photos` indices are positional: `fullscreenImageCache`, `renderedThumbnailNodes` and selection all break if the list is re-sorted without clearing/re-finding them. A page change replaces the whole list, so it clears the selection first.
- ⚠ sensitive: `view_fix` must not be applied to a thumbnail or generated preview (double rotation). The fullscreen thumbnail stage therefore calls `setSlotImageSize(slot, w, h, 1)`; the sharp image that replaces it uses the photo's own `view_fix`.
- Compare mode: selection limited to 4 only while it is active (`limitSelectionForCompare` when entering it).
- No frontend framework (AGENTS.md §4.6).

## How to extend
1. New thumbnail layout: a branch in `layoutPhotoRange`, handling in `scheduleJustifiedRelayout` and `renderVisibleItems` (`object-fit`), option in `index.html` and `defaults.jsonc` (`recipes.md` §2).
2. New per-thumbnail badge: create it once in `renderVisibleItems` (lazily), update it only when the value changes.
3. New marking field: add a `MARKING_PROPERTIES` entry and a `setSelection…` function using `writeMarking`; backend field in `update_photos_marking`.
4. New viewable format: extension list in `format-filters.js` (`recipes.md` §4) and, if the webview cannot show it, `needsGeneratedPreview` + backend preview.
